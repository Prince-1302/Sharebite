# ShareBite — Food Waste Management Platform with ML-Assisted Recommendations

A full-stack platform that connects **restaurants**, **NGOs** and **administrators** to move surplus food from waste to donation. It combines a Next.js/TypeScript frontend, a Flask ML inference API (4 scikit-learn Random Forest models trained on a 15,000-row synthetic dataset) and an LLM-based recipe helper.

## 1. Problem Statement

Restaurants discard edible surplus while NGOs lack a reliable way to find it. ShareBite provides one workflow for expiry-aware inventory tracking, ML-assisted donation/priority/waste-risk recommendations, donation and disposal hand-off to NGOs, and impact reporting. The landing page cites three global statistics (1.3 billion tons wasted/year, $1 trillion cost, 8% of emissions) as hard-coded marketing copy; the repo gives no source for them.

Two Flask entry points exist:

## 4. Dataset and Data Engineering ✅

Generated by `generate_dataset.py` (seeded: `np.random.seed(42)`, `random.seed(42)`) and stored as `food_waste_dataset.csv`.

| Property | Value | Source |
|---|---|---|
| Type | **Synthetic** (simulated, not real restaurant data) | `generate_dataset.py` |
| Records | **15,000** | CSV (`shape` = 15000 × 21) |
| Columns | **21** | CSV |
| Food categories | **10** (Fruits, Vegetables, Dairy, Meat, Bakery, Grains, Beverages, Prepared Foods, Frozen Foods, Canned Goods) | CSV |
| Restaurant types | **6** (Fast Food, Fine Dining, Cafe, Buffet, Food Truck, Bakery) | CSV |
| Missing values | 0 | CSV |
| Exact duplicate rows | 9 (not removed) | CSV |
| Purchase-date span | 2024-11-18 → 2025-11-18 (one year) | CSV |
| Quantity | mean 49.96, min 1, max 194 | CSV |
| Outcome mix (`final_status`) | consumed 74.22% · donated 13.09% · expired 12.69% | CSV |
| `should_donate` target | 87.11% positive (13,066) / 12.89% negative (1,934) | CSV |

**How the data is simulated.** Each category has a shelf-life range and base waste probability; each restaurant type has an average quantity and waste factor. Shelf life is sampled uniformly within the category range, quantity from a normal distribution (σ = 30% of the restaurant mean), and outcome (consumed/expired/donated) from `waste_probability × (1 + waste_factor)`, plus a 15% proactive-donation rule for high-quantity items.

**Feature engineering (`train_models.py → prepare_features`)** — **18 features** = 9 base + 9 engineered:

- Base (9): `category_encoded`, `restaurant_type_encoded`, `quantity`, `days_remaining`, `shelf_life`, `month`, `day_of_week`, `is_weekend`, `waste_probability`
- Engineered (9): `quantity_expiry_interaction`, `category_waste_interaction`, `is_perishable`, `high_quantity` (≥30), `very_high_quantity` (≥50), `quantity_perishable_interaction`, `is_expired`, `expiring_today` (≤1 day), `expiring_soon` (≤7 days)

**Split:** 80/20 `train_test_split(random_state=42)` → **12,000 train / 3,000 test** per model. No separate validation set. ✅

## 5. AI/ML Implementation ✅

| # | Model | Algorithm | Target | Task |
|---|---|---|---|---|
| 1 | `expiration_predictor` | RandomForestRegressor | `days_remaining` | Regression |
| 2 | `waste_risk_predictor` | RandomForestRegressor | `waste_risk` (0–100) | Regression |
| 3 | `donation_recommender` | RandomForestClassifier | `should_donate` (0/1) | Binary classification |
| 4 | `priority_scorer` | RandomForestRegressor | `priority_score` (0–100) | Regression |

All four use `n_estimators=100`, `max_depth=15`, `min_samples_split=5`, `random_state=42`, `n_jobs=-1`. These are **fixed hyperparameters** — no grid/random search, no algorithm comparison was run. Models are serialized with `joblib` together with `feature_info.joblib` (18 column names plus a category mapping). `StandardScaler` is imported but not used.

### Inference workflow (`ml_api.py`)
1. Parse request (`category`, `restaurant_type`, `quantity`, `purchase_date`, `expiry_date`).
2. Compute `days_remaining` from today's date and `shelf_life` from purchase → expiry.
3. Rebuild the same 18-feature vector used in training.
4. Predict with the model, then apply a **hybrid layer**:

| Endpoint | ML component | Rule component |
|---|---|---|
| `/predict/expiration` | Model used only if `expiry_date` missing | Date arithmetic used whenever `expiry_date` is given |
| `/predict/waste-risk` | 70% model + 30% rule-adjusted risk | Floors: ≤1 day → ≥80, ≤3 days → ≥60, ≤7 days → ≥40; expired → 100 |
| `/predict/donation` | 80% `predict_proba` + 20% rule score | Threshold 0.45 on blended probability |
| `/predict/priority` | Model used only when > 7 days remain (80% ML + 20% urgency) | Fixed bands for ≤ 7 days; expired → 100 |
| `/predict/all` | All four | Combined response with risk/priority levels |

## 6. Model Performance 🔁

Re-running `train_models.py` on `food_waste_dataset.csv` produced the numbers below. The saved `.joblib` files were also re-evaluated on the same 3,000-row test split and give identical results.

### Donation recommender (classification, test n = 3,000)

| Metric | Value |
|---|---|
| Accuracy | **98.77%** |
| ROC-AUC | **0.9958** |
| Precision / Recall / F1 (class 1 "donate") | 1.00 / 0.99 / **0.9929** |
| Precision / Recall (class 0) | 0.91 / 1.00 |
| Confusion matrix `[[TN, FP], [FN, TP]]` | `[[369, 1], [36, 2594]]` |
| 5-fold CV accuracy | 98.47, 98.60, 98.93, 98.47, 98.60 → **mean 98.61%** |
| Training accuracy | 99.01% |
| Majority-class baseline | 87.11% |

### Regression models (test n = 3,000)

| Model | MAE | RMSE | R² |
|---|---|---|---|
| Expiration predictor | 0.054 days | 0.232 days | ≈ 1.000 |
| Waste-risk predictor | 0.069 | 0.439 | 0.9998 |
| Priority scorer | 0.001 | 0.005 | ≈ 1.000 |

### ⚠️ How to interpret these numbers (target leakage)

The near-perfect scores come from how the synthetic labels are built, not from real-world predictive skill. Verified in the code and data:

- **Expiration predictor:** the target `days_remaining` is also an input feature (correlation 1.0; feature importance 0.9997).
- **Priority scorer:** `priority_score` is an exact deterministic function of `shelf_life` and `quantity` (max difference 0.0 when recomputed); `shelf_life` has importance 0.98.
- **Waste-risk predictor:** the label is computed from `waste_probability`, `days_remaining` and `quantity`, all of which are inputs (`waste_probability` importance 0.94).
- **Donation recommender:** a 4-condition rule on input features reproduces 98.63% of `should_donate` labels; the model scores 98.77%. Its recall on the minority "don't donate" class is 99.7% (369/370).

So the models demonstrate that Random Forests can **learn the synthetic labeling rules**. They are not evidence of accuracy on real restaurant data. No real-world validation exists.

## 7. Known Engineering Issues Found in Audit ⚠️

| # | Issue | Impact |
|---|---|---|
| 1 | **Train/serve encoding mismatch.** Training encodes categories with `pd.Categorical(...).codes` (alphabetical: Bakery=0 … Vegetables=9; Bakery=0, Buffet=1 … for restaurant types). `ml_api.py` hard-codes a different mapping (Fruits=0, Vegetables=1 …; Fast Food=0 …). `feature_info.joblib` stores a third (first-appearance) order. | Categorical inputs reach the models with the wrong codes; fix by loading the mapping from training |
| 2 | `days_remaining` in training is measured from the dataset's generation date (74.6% of rows already "expired"); the API measures from today | Distribution shift between training and serving |
| 3 | `load_models()` runs only under `if __name__ == '__main__'` | `gunicorn ml_api:app` would start with no models loaded |
| 4 | Procfile runs `app.py` (rule-only) | Production API does not use trained models |
| 5 | `status = 'expired'` branch in `generate_dataset.py` is unreachable (`<= 3` is tested first) | Dead code |
| 6 | `/health` in `app.py` always returns `models_loaded: true` | Misleading health check |
| 7 | `app.py`: unit `g` is treated as `kg`; invalid date becomes 0 days | Input-handling edge cases |
| 8 | Legacy `food_waste_model.pkl` (single 50-tree regressor, 3 features) is not produced by `train_models.py` and is used by neither API | Stale artifact |

## 8. Backend and API Architecture ✅

**`ml_api.py` — 6 routes** (Flask, Flask-CORS with default open origins)

| Method | Route | Purpose |
|---|---|---|
| GET | `/health` | Reports whether models are loaded |
| POST | `/predict/expiration` | Days until expiry |
| POST | `/predict/waste-risk` | Risk score + Low/Medium/High |
| POST | `/predict/donation` | `should_donate` + blended probability |
| POST | `/predict/priority` | Priority score + level |
| POST | `/predict/all` | All predictions in one call |

Example request:
```json
{ "category": "Fruits", "restaurant_type": "Fast Food", "quantity": 50,
  "purchase_date": "2026-11-15", "expiry_date": "2026-11-25" }
```
Error handling: every route wraps logic in `try/except` and returns HTTP 400 with `{success:false, error}`; `/predict/all` returns HTTP 500 if models are missing.

**`app.py` — 6 routes** (`/`, `/health`, `/predict/all`, `/predict/waste-risk`, `/predict/donation`, `/api/recipe` stub). Pure rules: donation tiers (0.95/0.75/0.45/0.15), risk = 0.6 (<3 days) + 0.3 (qty > 10). Reads `PORT` from the environment (default 10000).

## 16. Challenges and Engineering Decisions

- **Time-based features:** the original `days_until_expiry` (shelf life) was replaced with `days_remaining` (from today) so predictions reflect real-time urgency (noted in code comments).
- **Hybrid ML + rules:** rule floors guarantee sensible output for expired or near-expiry items, and the donation threshold was lowered to 0.45 to make recommendations more proactive.
- **Expiry source of truth:** explicit expiry dates override the model, avoiding unnecessary regression error.
- **Decoupled ML service** so the web app keeps working if inference is unavailable.
- **Reproducible pipeline:** fixed seeds, one-command scripts (`run_training.sh/.bat`).

## 17. Future Improvements 🗺️

- Fix the encoding mismatch (load mappings from `feature_info`), and compute `days_remaining` relative to each row's purchase date (or retrain regularly) to remove date drift.
- Remove target leakage (drop label-defining features) and train on real or independently simulated labels.
- Add hyperparameter search and model comparison (e.g., Gradient Boosting, XGBoost).
- Add pytest for APIs, Jest/Playwright for UI, and CI.
- Run `ml_api.py` (not `app.py`) in production; load models at import time.
- Real backend and database, password hashing, JWT, restricted CORS.
